Sound Blaster 16 ISA profiles
============================

The existing ``sb16-generic`` model implements a legacy Sound Blaster
16-compatible DSP and mixer on ISA, plus an integrated analog gameport
by default.
The DSP version, audio I/O, IRQ, DMA properties and DSP migration fields
remain unchanged. It does not expose ISA Plug and Play card identification.

Creative CT1740 (non-PnP)
------------------------

The ``sb16`` device is a distinct QOM profile targeting the CT1740 with
DSP revision 4.05. It shares the existing PCM engine but enforces
the board's documented jumper selections:

* Digital audio base: 0x220 (default), 0x240, 0x260 or 0x280.
* IRQ: 5 (default), 7, 9 (PC/AT routing of IRQ2) or 10.
* 8-bit DMA: 0, 1 (default) or 3.
* 16-bit DMA: 5 (default), 6 or 7.
* Gameport: enabled by default; ``gameport=off`` models JYEN open.

Example::

    -audiodev none,id=snd -device sb16,audiodev=snd

The current profile holds IRQ and DMA assignments fixed, and the
mixer's 80h and 81h readback cannot drift away from the wired resources.
This is a fixed-resource implementation boundary, not a claim that
all non-PnP SB16 revisions have read-only setup registers. Acknowledging
one pending PCM interrupt preserves the other pending source. The
mapped DSP/mixer I/O ports are checked before realization.

The original CT1740 also contains OPL3 FM synthesis, a Creative/Panasonic
CD-ROM interface and an analog mixer. These are not fully modeled; the
shared DSP is not a cycle-accurate CT1741 implementation. This profile
represents a board without the optional CT1748 ASP/CSP coprocessor.
CSP probe commands consume their arguments but cannot store register
values; reads return 0xff as an emulation absence convention, not a
measurement of physical bus timing. The legacy generic profile retains
its existing CSP register compatibility behavior. Migration
is disabled for this new profile pending a board-specific state
contract. The generic type and its migration state remain unchanged.
Use ``-device sb16-generic`` for the previous compatibility model.

MPU-401 UART MIDI
-----------------

The CT1740 now automatically realizes a reusable
``mpu401-uart-compat`` ISA child, even with ``-nodefaults``. Its MIDI
port defaults to 0x330; ``mpu-iobase=0x300`` selects the alternate
MSEL jumper setting. Register 82h bit 2 reports the MIDI interrupt
on the same IRQ as the two PCM sources. Reading the MIDI data port
acknowledges only MIDI; DSP acknowledgments and DSP reset do not
clear pending MIDI data.

The UART implements reset (FFh), UART entry (3Fh), FEh acknowledgments,
active-low status bits, raw receive bytes and a timed transmit holding
register. The MIDI serial frame is modeled at 31.25 kbaud. Reset ACK is
pollable; UART entry and inbound data assert the MIDI interrupt.
Receive capacity is a bounded 256-byte emulation buffer, not a claim
about the CT1741's physical FIFO depth. No intelligent MPU-401 mode,
host synthesizer, MIDI message interpretation, electrical signaling,
or separate SB-MIDI DSP mode is provided.

A raw character backend is optional. Without one, MIDI output leaves
the virtual UART without producing sound. To capture outgoing bytes
to a QEMU ring buffer without attaching host hardware::

    -audiodev none,id=snd -chardev ringbuf,id=midi,size=4096 \
    -device sb16,audiodev=snd,midi-chardev=midi

The standalone interface can also be used on an ISA machine::

    -chardev ringbuf,id=midi,size=4096 \
    -device mpu401-uart-compat,iobase=0x330,irq=9,chardev=midi

Other sound boards can use the same child device and wire its named IRQ
output to their own mixer/interrupt controller with the internal
shared-IRQ sentinel. Do not add a standalone device on top of the
CT1740's MIDI ports; conflicting I/O mappings fail realization.
The standalone device and CT1740 are currently unmigratable.
The generic SB16 remains unchanged.

Reference: Creative Sound Blaster Series Hardware Programming Guide,
chapter 2 (interrupt sharing) and chapter 5 (MPU-401 UART mode),
https://pdos.csail.mit.edu/6.828/2018/readings/hardware/SoundBlaster.pdf

Later ISA Plug and Play
-----------------------

The ``sb16-pnp`` name is reserved for the later Creative ISA Plug and Play
family. The QOM profile is built with ``CONFIG_SB16_PNP`` when SB16 and the
ISA bus are enabled. It deliberately rejects realization until ISA PnP serial
isolation, logical device enumeration and resource activation exist. Do not
use it in an existing guest configuration yet.

Hardware identity
-----------------

Linux's SB16 ISA driver lists card IDs CTL0024 through CTL002C with audio
logical device ID CTL0031. These are family references, not a selection of
a verified board revision. ViBRA and AWE devices remain separate.

Windows 95/98 may display a combined Sound Blaster 16 or AWE32 driver
description for the shared PCM interface. This is not an AWE32 hardware
identifier. The EMU8000 synthesizer requires independent detection at
its own I/O windows (normally 0x620, 0xa20 and 0xe20); neither legacy
SB16 profile claims those ports. Do not install an AWE wavetable driver
on the basis of a DSP 4.xx version or a shared driver label alone.
The CT1748 ASP/CSP is a separate optional effects processor, not an
EMU8000. The CT1740 tests check both absent CSP and absent EMU8000
without changing the legacy generic DSP compatibility contract.

must not be generalized to every PnP SB16.

Implementation boundary
-----------------------

The PnP configuration state belongs in a shared ISA subsystem. A complete
model will need to route its assigned I/O, IRQ and DMA resources to the audio
engine only when the logical device is active. Deactivation must not leave
stale I/O or DMA registrations. Do not advertise unimplemented logical
devices or reuse fixed legacy mappings while claiming PnP support.

Analog gameport
---------------

The SB16 and many AWE32 boards provide a separate analog joystick
interface at I/O port 0x201, independent of the DSP, mixer and MIDI.
The following explicit ISA device profiles share the IBM-compatible
resistance-to-time interface:

* ``isa-gameport``: generic analog port.
* ``ibm-game-control``: IBM PC Game Control Adapter interface.
* ``creative-gameport``: Creative legacy analog gameport interface.

The ``sb16-generic`` device automatically creates a Creative gameport
child on the same ISA bus unless ``gameport=off`` is specified. There is no additional
IRQ or DMA assignment. To test a simulated centered joystick A with an
existing SB16 configuration, append::

    -global creative-gameport.connected=3

For independent adapters, disable the SB16 gameport first. For example::

    -device sb16-generic,audiodev=snd,gameport=off -device ibm-game-control,connected=3

Use the existing audio backend ID in place of ``snd``. Do not attach a
second gameport at 0x201; conflicting mappings are rejected.

The four-bit ``connected`` mask selects attached analog axes (A-X, A-Y,
B-X, B-Y, in that order); the four-bit ``buttons`` mask selects pressed
buttons. Axis values are fixed resistances in ohms (0-100000). No axes
or buttons are connected by default. A disconnected analog input reads
high; connected axes time out according to the IBM reference formula on
the virtual clock. Buttons are active-low. No IRQ or DMA is required.
Only byte accesses to 0x201 are implemented. The profile and input
properties must match across migration.

The standalone profiles remain opt-in. The integrated child has its own
migration state, so both endpoints must use matching topology and input
properties. For a saved state from before SB16 gained its gameport, set
``gameport=off`` to preserve the old topology, or cold boot with the new
default. No host controller input, ISA PnP identifiers, MIDI,
SideWinder digital protocol, or board-specific jumper state is emulated.
This interface does not change the Windows generic driver name. The
Creative profile represents the documented compatible interface, not a
complete model of a particular Creative board.

Reference: IBM Personal Computer Technical Reference (August 1981),
Game Control Adapter, pp. 2-117 to 2-122; Creative Sound Blaster 16
User's Guide, Connecting a Joystick (p. 2-3) and Appendix B.
