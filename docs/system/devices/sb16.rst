Sound Blaster 16 ISA profiles
============================

The existing ``sb16-generic`` model implements a legacy Sound Blaster
16-compatible DSP and mixer on ISA, plus an integrated analog gameport
by default.
The DSP version, audio I/O, IRQ, DMA properties and DSP migration fields
remain unchanged. It does not expose ISA Plug and Play card identification.

Creative CT1740 (non-PnP)
------------------------

The canonical ``sb16-ct1740`` device (alias ``sb16``) targets the CT1740 with
DSP revision 4.05 by default. Versions 4.04 and 4.11 are also accepted
as reported for CT1740 boards. It shares the existing PCM engine but enforces
the board's documented jumper selections:

* Digital audio base: 0x220 (default), 0x240, 0x260 or 0x280.
* IRQ: 5 (default), 7, 9 (PC/AT routing of IRQ2) or 10.
* 8-bit DMA: 0, 1 (default) or 3.
* 16-bit DMA: 5 (default), 6 or 7.
* Gameport: enabled by default; ``gameport=off`` models JYEN open.

Example::

    -audiodev none,id=snd -device sb16-ct1740,audiodev=snd

The current profile holds IRQ and DMA assignments fixed, and the
mixer's 80h and 81h readback cannot drift away from the wired resources.
This is a fixed-resource implementation boundary, not a claim that
all non-PnP SB16 revisions have read-only setup registers. Acknowledging
one pending PCM interrupt preserves the other pending source. The
mapped DSP/mixer I/O ports are checked before realization.

The original CT1740 also contains OPL3 FM synthesis, a Creative/Panasonic
CD-ROM interface and an analog mixer. These are not fully modeled; the
shared DSP is not a cycle-accurate CT1741 implementation. This profile
represents a board without the optional CT1748 ASP/CSP coprocessor.
CSP probe commands consume their arguments but cannot store register
values; reads return 0xff as an emulation absence convention, not a
measurement of physical bus timing. The legacy generic profile retains
its existing CSP register compatibility behavior. Migration
is disabled for this new profile pending a board-specific state
contract. The generic type and its migration state remain unchanged.
Use ``-device sb16-generic`` for the previous compatibility model.

CT1730 and CT1740 identity
~~~~~~~~~~~~~~~~~~~~~~~~~

Creative's product catalog identifies CT1730 as Sound Blaster 16 and
CT1740/CT1748 as Sound Blaster 16 CSP. Historical records identify the
CT1740 PCB as the June 1992 launch design. Collector observations show
CT1730-labelled cards using CT1740-marked PCBs with DSP 4.05. The exact
retail chronology of the two model labels is unresolved. Keep the CT1730
as a separate product profile, not an earlier hardware generation inferred
from its number. Both share the documented jumper table. CT1730's previous
4.04 default was not supported by equivalent sticker evidence; retain
explicit 4.04 for existing configurations, but default to observed 4.05.
A CT1740 with an operational ASP/CSP is not implemented.

CT1745 mixer register behavior
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The fixed-jumper profiles share the CT1745 register model. The legacy
four-bit stereo volume registers 04h, 22h, 26h, 28h and 2Eh read and
write the corresponding five-bit volume controls at 30h through 39h.
Three-bit microphone register 0Ah shares the control at 3Ah. Compatibility
writes clear the extra precision bits; this is a deterministic mapping
convention, not a verified measurement of low-bit hardware behavior.
Reset restores documented volume, routing, gain and tone register defaults
without changing ISA resource assignments or IRQ state. This corrects
guest register readback only; analog gain, filtering and routing are
not implemented by these changes. The generic SB16 remains unchanged.

Reference: Creative Sound Blaster Series Hardware Programming Guide,
chapter 4, CT1745 mixer, pp. 4-12 through 4-17.

CT1741 DSP command handling
~~~~~~~~~~~~~~~~~~~~~~~~~~~

The named fixed-jumper profiles implement DSP 4.xx speaker status (D8h)
and keep the D1h/D3h flag independent of PCM playback. DMA pause, resume
and auto-init exit commands apply to the current transfer width only;
resume requires a paused transfer. Starting a new PCM transfer releases
the old DMA request, and reset clears paused state and the time constant.
Bxh/Cxh lengths count individual samples, not stereo frames, so single
cycle and auto-init use the same sample-to-byte conversion. Named profiles
stop each DMA service at the programmed controller buffer boundary and
return the terminal byte position without wrapping it. The ISA DMA
controller latches terminal count and reloads address and count only if
the controller's own auto-init mode is enabled. DSP block IRQs remain
independent of controller terminal count. The generic SB16 retains its
historical wrapping behavior.

Unsupported ADPCM (16h/17h/1Fh), ADC (24h/2Ch) and DSP MIDI commands
(30h/31h/34h-38h) are recognized for command framing only. Parameter
bytes are consumed without starting playback, recording or UART mode.
Incomplete commands are discarded on reset; unsupported ADPCM and E2h
parameters cannot contaminate the following command. MPU-401 UART is
still a separate interface. This change does not implement DSP MIDI,
ADPCM decoding, ADC, DMA identification, independent capture timing,
direct DAC playback, or cycle-accurate DSP firmware behavior.
The generic SB16 retains the prior command semantics and migration state.

Reference: Creative Sound Blaster Series Hardware Programming Guide,
chapter 6 (DSP command descriptions, especially Bxh/Cxh and D0h-DAh),
https://cecas.clemson.edu/~ahoover/ece468/labs/SoundBlasterProgrammingGuide.pdf

These are experimental PCM/MIDI subsets, not complete boards. The reported
DSP revisions do not yet reproduce revision-specific firmware behavior
(including MIDI hanging-note bugs). The optional CSP, OPL3 and storage
controllers remain unimplemented; none of these profiles registers their
storage I/O ports. The DSP minor revision is a binary number: use
``version=0x040b`` for 4.11 and ``version=0x040c`` for 4.12.
All four new profiles are unmigratable, like the CT1740.

For example::

    -audiodev none,id=snd -device sb16-ct1790,audiodev=snd

Later CT2230/CT2290 and ViBRA boards are not registered by this change;
their resource-selection and mixer differences need separate modeling.

MPU-401 UART MIDI
-----------------

The CT1740 now automatically realizes a reusable
``mpu401-uart-compat`` ISA child, even with ``-nodefaults``. Its MIDI
port defaults to 0x330; ``mpu-iobase=0x300`` selects the alternate
MSEL jumper setting. Register 82h bit 2 reports the MIDI interrupt
on the same IRQ as the two PCM sources. Reading the MIDI data port
acknowledges only MIDI; DSP acknowledgments and DSP reset do not
clear pending MIDI data.

The UART implements reset (FFh), UART entry (3Fh), FEh acknowledgments,
active-low status bits, raw receive bytes and a timed transmit holding
register. The MIDI serial frame is modeled at 31.25 kbaud. Reset ACK is
pollable; UART entry and inbound data assert the MIDI interrupt.
Receive capacity is a bounded 256-byte emulation buffer, not a claim
about the CT1741's physical FIFO depth. No intelligent MPU-401 mode,
host synthesizer, MIDI message interpretation, electrical signaling,
or separate SB-MIDI DSP mode is provided.

A raw character backend is optional. Without one, MIDI output leaves
the virtual UART without producing sound. To capture outgoing bytes
to a QEMU ring buffer without attaching host hardware::

    -audiodev none,id=snd -chardev ringbuf,id=midi,size=4096 \
    -device sb16-ct1740,audiodev=snd,midi-chardev=midi

The standalone interface can also be used on an ISA machine::

    -chardev ringbuf,id=midi,size=4096 \
    -device mpu401-uart-compat,iobase=0x330,irq=9,chardev=midi

Other sound boards can use the same child device and wire its named IRQ
output to their own mixer/interrupt controller with the internal
shared-IRQ sentinel. Do not add a standalone device on top of the
CT1740's MIDI ports; conflicting I/O mappings fail realization.
The standalone device and CT1740 are currently unmigratable.
The generic SB16 remains unchanged.

Reference: Creative Sound Blaster Series Hardware Programming Guide,
chapter 2 (interrupt sharing) and chapter 5 (MPU-401 UART mode),
https://pdos.csail.mit.edu/6.828/2018/readings/hardware/SoundBlaster.pdf

Wave Blaster expansion interface
--------------------------------

The CT1740's optional wavetable daughterboard is driven by the existing
MPU-401 UART, not by another ISA controller. Named fixed-jumper profiles
now expose a separate, optional transmit-only raw character endpoint
``waveblaster-chardev``. It models MIDI delivery to a daughterboard
connector independently of the external MIDI endpoint. Both receive the
same serialized bytes, with one 320 us frame per byte. No new guest I/O,
IRQ, DMA channel, PnP identity or EMU8000 registers are allocated.
Disabling the gameport does not disable MIDI, as Creative's SB16 manual
specifies.

For example, observe both outputs without sound synthesis::

    -audiodev none,id=snd -chardev ringbuf,id=external,size=4096 \\
    -chardev ringbuf,id=wave,size=4096 \\
    -device sb16,audiodev=snd,midi-chardev=external,waveblaster-chardev=wave

A host backend that temporarily cannot accept a byte can delay completion
of the UART holding register, as in the existing external MIDI transport.
Each sink has independent completion tracking so retries never duplicate
bytes already delivered to the other sink. Reset cancels an outstanding
frame, but cannot retract bytes already delivered. The daughterboard
endpoint does not provide MIDI input or generate IRQs. Unconnected
endpoints discard output.

Optional SoundFont synthesis
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The separate ``waveblaster-soundfont`` property attaches a software
wavetable synthesizer to the existing connector. It requires the
Fsynth fork (https://github.com/retrochristian5000/Fsynth), at commit
767cebc7ba29b9cf4760dc81bbb80d50a6e9f27f or a compatible descendant.
Install that library and its development headers in an explicit prefix;
select its pkg-config directory and configure QEMU with
``--enable-fsynth`` (Meson ``-Dfsynth=enabled``). Configuration checks
the fork's embedded stream API by compiling and linking, not just its
version. The dependency is disabled by default and ordinary upstream
FluidSynth without the stream API does not satisfy the check.

Example with an existing, locally licensed SoundFont::

    -audiodev coreaudio,id=snd \\
    -device sb16,audiodev=snd,waveblaster-soundfont=/path/to/bank.sf2

QEMU owns the stereo audio voice and output backend; Fsynth does not
open another audio driver. MIDI frames reach the synth once at the
existing UART completion deadline, independent of backend retry.
The synth uses 44.1 kHz stereo, 64 voices and one synthesis core, with
bounded 512-frame PCM staging and retained short writes. The CT1745
master and MIDI register values apply an approximate linear gain to
newly rendered PCM. This is not calibrated analog attenuation.
Machine reset clears the synthesizer and partial stream, while the
MPU UART reset command only resets the UART. Already queued backend
audio may still drain. No new ISA I/O, IRQ, DMA or PnP identity is added.
The optional endpoint can coexist with the external raw MIDI outputs.

This is generic SoundFont synthesis, not a CT1900, CT1910, DB50XG or
SCB-55 hardware model. No instrument ROM is bundled. The exact analog
mixer curve, effects, input routing and sample-accurate guest MIDI/audio
synchronization remain future work. The generic SB16 is unchanged and
the named board remains unmigratable. A missing library or invalid
SoundFont fails explicitly instead of silently producing no sound.
Set ``QTEST_WAVEBLASTER_SOUNDFONT`` to a local SF2 fixture for the optional
QTest startup, MIDI transmission and machine reset case; the error case
runs without a fixture.

References: Creative Sound Blaster 16 User's Guide, pp. 2-3 to 2-4,
Appendix A-8, Appendix C-3:
https://datassette.s3.us-west-004.backblazeb2.com/manuais/sound_blaster_16_users_guide.pdf

Later ISA Plug and Play
-----------------------

The ``sb16-pnp`` name is reserved for the later Creative ISA Plug and Play
family. The QOM profile is built with ``CONFIG_SB16_PNP`` when SB16 and the
ISA bus are enabled. It deliberately rejects realization until ISA PnP serial
isolation, logical device enumeration and resource activation exist. Do not
use it in an existing guest configuration yet.

Implementation boundary
-----------------------

The PnP configuration state belongs in a shared ISA subsystem. A complete
model will need to route its assigned I/O, IRQ and DMA resources to the audio
engine only when the logical device is active. Deactivation must not leave
stale I/O or DMA registrations. Do not advertise unimplemented logical
devices or reuse fixed legacy mappings while claiming PnP support.

Analog gameport
---------------

The SB16 and many AWE32 boards provide a separate analog joystick
interface at I/O port 0x201, independent of the DSP, mixer and MIDI.
The following explicit ISA device profiles share the IBM-compatible
resistance-to-time interface:

* ``isa-gameport``: generic analog port.
* ``ibm-game-control``: IBM PC Game Control Adapter interface.
* ``creative-gameport``: Creative legacy analog gameport interface.

The ``sb16-generic`` device automatically creates a Creative gameport
child on the same ISA bus unless ``gameport=off`` is specified. There is no additional
IRQ or DMA assignment. To test a simulated centered joystick A with an
existing SB16 configuration, append::

    -global creative-gameport.connected=3

For independent adapters, disable the SB16 gameport first. For example::

    -device sb16-generic,audiodev=snd,gameport=off -device ibm-game-control,connected=3

Use the existing audio backend ID in place of ``snd``. Do not attach a
second gameport at 0x201; conflicting mappings are rejected.

The four-bit ``connected`` mask selects attached analog axes (A-X, A-Y,
B-X, B-Y, in that order); the four-bit ``buttons`` mask selects pressed
buttons. Axis values are fixed resistances in ohms (0-100000). No axes
or buttons are connected by default. A disconnected analog input reads
high; connected axes time out according to the IBM reference formula on
the virtual clock. Buttons are active-low. No IRQ or DMA is required.
Only byte accesses to 0x201 are implemented. The profile and input
properties must match across migration.

The standalone profiles remain opt-in. The integrated child has its own
migration state, so both endpoints must use matching topology and input
properties. For a saved state from before SB16 gained its gameport, set
``gameport=off`` to preserve the old topology, or cold boot with the new
default. No host controller input, ISA PnP identifiers, MIDI,
SideWinder digital protocol, or board-specific jumper state is emulated.
This interface does not change the Windows generic driver name. The
Creative profile represents the documented compatible interface, not a
complete model of a particular Creative board.

Reference: IBM Personal Computer Technical Reference (August 1981),
Game Control Adapter, pp. 2-117 to 2-122; Creative Sound Blaster 16
User's Guide, Connecting a Joystick (p. 2-3) and Appendix B.


Experimental CT1741 firmware execution
-------------------------------------

Named fixed-jumper SB16 profiles accept an explicit ``dsp-firmware``
path to an exactly 8192-byte raw MCU ROM. The independent interpreter
supports ``intel-8052`` and ``intel-80c52`` model identities; the latter
is the default for this experimental CT1741 path. The models currently
share instruction semantics, not cycle-accurate timers or power behavior.
8051 and 80C51 are not registered as aliases. Example::

    -audiodev none,id=snd -device sb16,audiodev=snd,dsp-cpu=intel-8052,dsp-firmware=/path/to/ct1741.bin

The firmware executes from its own ROM, with 256 bytes of internal RAM,
separate SFRs and an XDATA host latch. P1 bits 0 and 1 report the output
and input latch state respectively. ISA DSP reset and command/status/data
ports connect to those latches instead of the compatibility command
handler. Machine reset restarts the MCU. Execution is bounded to 64
instructions per 64 us virtual timer event; this is an approximation,
not Intel machine-cycle timing. Unsupported instructions stop execution
and log the failing PC. No proprietary firmware is bundled.

This mode is experimental: firmware now controls the board PCM/DMA
engine and DSP audio IRQs through a private XDATA mailbox. MCU timers,
MCU interrupt handling, external program memory, serial, capture and ADPCM
remain unimplemented. Windows 98 playback is not
validated. Without the property, the existing SB16 PCM model is used
unchanged. Firmware mode remains unmigratable with the named boards.

References: Intel MCS-51 Microcontroller Family User's Manual,
https://web.mit.edu/6.115/www/document/8051.pdf ; independent CT1741
implementation https://sources.debian.org/src/mame/0.289%2Bdfsg1-1/src/devices/sound/ct1741.cpp .

Set ``QTEST_CT1741_FIRMWARE`` to the independently built identification
ROM to exercise reset, version and identification with the actual MCU
program in the SB16 qtest. Without the fixture that case is skipped;
the built-in instruction and latch tests require no external ROM.


Default firmware provider
~~~~~~~~~~~~~~~~~~~~~~~~~

When the WHP build selects SeaBIOS for i386 or x86_64 system firmware
and SB16 support is present, Meson discovers the independent SDCC and
makebin tools. If both are installed it builds and installs
``seabios-ct1741.bin`` as a separate ROM under the usual QEMU data
directory (subject to ``install_blobs``). The source remains in
``roms/seabios/firmware/ct1741/``; no ROM bytes are checked into the QEMU
repository. The x86 BIOS build does not require SDCC. The explicit target
``whp-seabios-ct1741`` is available when both tools and the SeaBIOS source
build are configured.

Use ``-device sb16,audiodev=snd,dsp-firmware=auto`` to request the default
SeaBIOS provider ROM, located through the normal firmware search path,
including ``-L``. An explicit ROM path remains supported. If the provider
image is missing or has the wrong size, realization fails rather than
silently changing DSP implementations. Selecting a different system BIOS
at runtime does not replace a peripheral's ROM; it is an independent
device. The ordinary SB16 command without a firmware property retains
the existing compatibility engine until firmware-driven audio is validated.

PCM hardware interface v1: the MCU writes four argument bytes at XDATA
0101h through 0104h, then commits an operation at 0100h. This is a private
emulation interface, not a verified physical Creative register map. The
firmware parses and validates commands; QEMU validates the completed
hardware action and operates the existing board DMA and PCM engine.
The MCU owns reset and identification replies. DSP reset stops DMA and
clears pending PCM IRQs without clearing the independent MPU IRQ. ISA
reads of base+0Eh and base+0Fh acknowledge the respective IRQ sources.
With QTEST_CT1741_FIRMWARE set, qtests exercise 8/16-bit single-cycle and
auto-init playback, terminal count and IRQ acknowledgement using the
separately built ROM. No production default has changed.

DMA identification (E2h)
~~~~~~~~~~~~~~~~~~~~~~~~

Named fixed-jumper boards implement the undocumented E2h command as a
one-byte device-to-memory transfer on the configured 8-bit ISA DMA
channel. In firmware mode the MCU computes the stateful response and
commits mailbox action 9; otherwise the named compatibility DSP computes
the same response. The generic migratable SB16 path is unchanged.
The DMA controller observes the actual byte position and terminal count.
The DSP does not generate a PCM IRQ or a data-port response. Masked
requests wait for unmasking; reset or starting PCM cancels a pending
identification request. Identification is admitted only while playback
is idle. The sequence follows the independent DOSBox-X implementation
of the undocumented command, not a verified physical CT1741 trace:
https://dosbox-x.com/doxygen/html/sblaster_8cpp_source.html .
Qtests check guest memory, neighboring bytes, DREQ, terminal count,
IRQ absence, sequence progression and reset cancellation. Firmware
cases require QTEST_CT1741_FIRMWARE.

PCM output mixer
~~~~~~~~~~~~~~~~

Named CT1745 boards convert DMA samples into signed little-endian stereo
PCM before writing to the selected host audio backend. Mono samples are
routed to both channels with independent gain. The mixer applies the two
5-bit voice and master attenuators (2 dB steps) and 2-bit output gain
(6 dB steps), using fixed-point coefficients and clipping to S16. Mixer
register writes affect newly rendered samples, not already queued audio.
DSP 4.xx D1h/D3h affect speaker status only; they do not mute this path.
Backend credit is converted to guest bytes and decremented on accepted
writes; DMA reports only the accepted guest bytes. The generic board
keeps its existing format and migration behavior. Both the firmware and
named compatibility command paths use this hardware mixer.

This is a digital approximation, not a circuit simulation: tone controls,
analog filtering, non-PCM sources, DAC reconstruction and incomplete
stereo frames at a DMA boundary are not covered by this change. The
existing aligned DMA transfers remain the supported playback contract.
See Creative Sound Blaster Series Hardware Programming Guide, chapters
4 and 6. The standalone CT1745 PCM tests cover format conversion, mono
routing, asymmetric levels, reset attenuation and saturation.
